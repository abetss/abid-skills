Phase 2 · Backend

Cache invalidation strategy

We keep the read path simple: one cache layer, explicit invalidation events, and no TTL guessing on the hot path.

Every write to the sessions store publishes an invalidate:user event on the internal bus. Edge nodes subscribe and drop the affected keys within ~50 ms, so reads after writes never serve stale session data. Keys that are expensive to recompute — mostly aggregated dashboard stats — carry a 5-minute TTL as a safety net, but correctness never depends on it.

Why not Redis Cluster?

We evaluated it in Q3. The ops overhead was the blocker — see the comparison matrix below for the full tradeoff.

Flush is not instant under load

A full cache flush during peak traffic can stampede the database for 30–60 s. Use the per-key invalidation endpoint instead during business hours.

Never reuse session IDs across tenants

The store keys on session ID alone. Reusing an ID across tenants leaks data across the isolation boundary and is a reportable security incident.

details-fold

Overview→detail splits: an always-visible verdict line with the full reasoning behind a click. Native disclosure — no script.

Option A — Postgres with a TTL sweeper

Recommended: zero new infrastructure, and our access patterns are already relational.

Sessions live in a sessions table with a expires_at index; a 1-minute sweeper job deletes expired rows. Reads are a single indexed lookup (~1 ms p95 in staging), and writes ride the existing replication we already monitor.

The tradeoff is write volume: at peak we expect ~800 writes/s to one table, well inside our headroom but worth a load test before cutover.

Option B — Managed Redis

Viable fallback: fastest reads, but adds a new stateful system to operate.

Redis gives sub-millisecond reads and native TTLs, so no sweeper job. The cost is operational: failover semantics, a new monitoring surface, and a persistence model (AOF everysec) we would need to learn before trusting it with auth state.

If the Postgres load test misses the latency budget by more than 2×, this is the path we revisit first.

pros-cons

2–3 alternatives as headed columns of advantages and drawbacks — lighter than a matrix when tradeoffs share no common axes.

Build in-house on Postgres

We own the semantics, on infrastructure we already run.

Advantages

  • Zero new infrastructure or on-call surface
  • Full SQL for debugging and audit queries
  • Marginal cost is effectively zero at our scale

Drawbacks

  • We build and maintain the expiry sweeper ourselves
  • Peak write volume needs a load test before cutover

Buy a managed session service

Vendor owns storage, expiry, and replication.

Advantages

  • Nothing to operate — expiry and failover included
  • Fastest time to ship: SDK integration only

Drawbacks

  • Auth state leaves our infrastructure — security review required
  • Per-session pricing grows linearly with our heaviest cost driver
  • Migration path out is a rewrite, not an export

glossary

Vocabulary the rest of the page assumes — a scannable term/definition grid for 4+ terms.

RRF
Reciprocal Rank Fusion — merges two ranked lists by position (1/(60+rank)), ignoring the engines' incompatible raw scores.
embedding
A fixed-length vector of semantic coordinates; texts about the same thing land near each other regardless of wording.
ANN index
Approximate nearest-neighbor structure — trades a little recall for orders of magnitude of lookup speed at scale.
chunk
The unit of text one embedding represents; chunking decides what "one result" even means in dense search.

Push a branch

trigger · instant

Any push to a feature branch opens (or updates) the pull request and queues the CI workflow. Nothing reaches main until every later step passes.

git push -u origin feat/search-filters

CI checks

github actions · ~6 min

Runs ESLint, tsc --noEmit, and the Vitest suite in parallel jobs. A red job blocks merge and posts the failing shard back to the PR.

jobs:
  verify:
    run: pnpm lint && pnpm typecheck && pnpm test

Review approved?

decision · one maintainer approval required

Branch protection requires one approving review from a maintainer with no unresolved threads. Requested changes send the branch back to the author; CI re-runs on the next push.

Revise and push again

failure path · author

The author addresses the review comments, amends or adds commits, and pushes. The loop back through CI is expected — median is two rounds per PR.

Squash merge to main

github · ~10 s

The PR is squash-merged so main stays one commit per change. The merge commit tags the release notes draft automatically.

gh pr merge --squash --auto

Deploy to production

github actions · ~4 min

The deploy workflow builds the image, pushes it to the registry, and rolls it out. A failed health check aborts the rollout and reverts automatically.

on:
  push:
    branches: [main]

Live on prod

terminal · ~11 min total

Health checks green, the commit status flips to success, and a summary lands in #releases. The change is live for all users.
