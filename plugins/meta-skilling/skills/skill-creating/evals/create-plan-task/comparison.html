Fix 1: Remove the caller clause from description

Rule
Caller-agnostic (R1)
Assertion
M4

Why: A description must say what the skill does and when to use it — never name who invokes it. "Invoked by plan-prep" couples the skill to a specific caller. The gold keeps the two scenarios (initial breakdown / mid-execution) but frames them as when to use it, so the skill reads identically no matter who triggers it.

Before (original)
description: Create one implementation task in a plan-prep work folder. Writes a task/task-NN.md file with the full Context / Implementation / Verification / Post verification tasks structure, and inserts an entry in task/task-list.md. Invoked by plan-prep (Phase 2) during initial breakdown AND standalone when new bugs or scope arise mid-execution. Triggers on "add a task", "new task", "another task to the plan", "create plan task", or "/create-plan-task".
After (gold)
description: Create one implementation task in a plan-prep work folder. Writes a task/task-NN.md file with the full Context / Implementation / Verification / Post verification tasks structure, and adds its task/task-list.md entry when one isn't already present. Use when adding a task to an existing plan — during initial plan breakdown or when new bugs or scope surface mid-execution. Triggers on "add a task", "new task", "another task to the plan", "create plan task", or "/create-plan-task".
Assertion checked
M4 — Description must not name the invoking caller

Fix 2: Decide from STATE, not from the caller

Rule
Caller-agnostic (R1)
Assertion
J1 (judgment), M5

Why: This is the headline fix. The original keyed behavior on who called it and a magic mode: from-plan-prep marker the caller had to pass. The gold reads the distinguishing fact directly from the file: does a task-list entry already exist? Same behavior, zero coupling — it now works no matter how it's launched. This is the kind of fix a linter cannot detect, which is why the eval grades it by judgment (J1).

Before (original)
## Modes

This skill has two invocation modes. Detect mode from how the skill was invoked:

| Mode | How it's invoked | task-list.md behavior |
|------|------------------|------------------------|
| from-plan-prep | Called by plan-prep (Phase 2). Caller passes mode: from-plan-prep marker. | Entry already exists. Do not insert. Only create task-NN.md file. |
| standalone | Default. User invokes directly mid-execution. | Entry does not exist. Insert it. |
After (gold)
## task-list.md: insert an entry, or not

Whether to add a task-list.md entry depends on **whether one already exists for this task** — read it from the file, don't branch on how the skill was started. After computing the next task number (Step 1), look in task-list.md for an entry pointing to task-{NN}.md:

| State of task-list.md | Behavior |
|-------------------------|----------|
| Entry already present — full wave structure written up front when plan was broken down. | Do not insert. Only create task-NN.md file. |
| No entry yet — task added mid-execution (bug, scope shift, etc.). | Insert it after the last [ x] line in ## Tasks. |
Assertions checked
J1 — Logic decouples from caller; branches on observable state instead

Fix 4: Declare arguments and reference them bare

Rule
Declare args (R3) + bare $name (R4)
Assertion
M2, M3

Why: The skill had an argument-hint but never declared arguments, and referred to inputs as "First/Second positional arg." Declaring them and using bare $work_folder / $task_description makes the inputs real substitutable values and self-documenting.

Before (original)
argument-hint: [optional: work folder path] [optional: short task description] --- ## Inputs - **First positional arg (optional):** path to the work folder ... - **Second positional arg (optional):** short description of the task ... If the user did not pass a work folder path, auto-detect:
After (gold)
argument-hint: [optional: work folder path] [optional: short task description] arguments: [work_folder, task_description] --- ## Inputs - **$work_folder (optional):** path to the work folder ... - **$task_description (optional):** short description of the task ... If $work_folder was not provided, auto-detect:
Assertions checked
M2, M3 — Arguments declared and substitution references are bare (not backtick-wrapped)

Fix 5: Fix the broken markdown link

Rule
Structural / valid links
Assertion
M1

Why: Inside an example block, ](task-NN.md) parses as a real relative link to a file that doesn't exist → validator error. Using the {NN} placeholder marks it as a template, which the validator correctly skips. This is partly a validator limitation, but the placeholder is the right authoring fix either way.

Before (original)
In task/task-list.md, add this line: - [ ] [Task NN: Name](task-NN.md) — [one-line description] [depends on: Task XX / "none"]
After (gold)
In task/task-list.md, add this line: - [ ] [Task {NN}: Name](task-{NN}.md) — [one-line description] [depends on: Task XX / "none"]
Assertion checked
M1 — All relative links in code examples are valid or use template placeholders

Fix 6: KEEP legitimate plan-prep references

Rule
Don't over-correct
Assertion
J3 (judgment)

Why: The distinction between coupling and legitimacy is the whole point of Rule 1. "Invoked by plan-prep" (who calls me) is coupling and was removed. "plan-prep.md must exist first" (a prerequisite the user satisfies) is not coupling and was kept intentionally. A naive fix that deletes every mention of plan-prep would fail J3.

Before and After (unchanged — intentionally kept)
The work folder must already contain plan-prep.md and task/task-list.md — this skill does not bootstrap a plan from scratch. ## Prerequisites 1. {work-folder}/plan-prep.md exists. If not: > "I can't add a task without a > plan-prep.md in this work folder. > Run the plan-prep skill first to > establish requirements, landscape, > and flow."
Why this stayed (the guard)

These references are legitimate because they describe a prerequisite the user runs first and the artifact (plan-prep.md) — not coupling to a specific caller. Removing them would be over-correction and would break a real constraint the skill has.

Assertion checked
J3 — Prerequisite references to plan-prep are preserved; only caller-coupling is removed

Where to focus when reviewing

Fix 6: The trap
The easy mistake is over-correcting and scrubbing the legitimate prerequisite references. Gold keeps them on purpose. This is judgment call J3.
3
Fixes 1, 4, 5: The baseline
Mechanical and a competent agent may get them even without the skill. They are the floor, not the ceiling — what matters is whether the agent understood the decoupling logic deep enough to propagate it correctly.
